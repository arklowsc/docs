Metrics add the view from inside your systems. They can show pressure in a container, model deployment, provider quota, or some other resource before that pressure appears as degradation in your product.

## Metric model

Metrics connect to actions in four steps:

1. A **metric source** connects Arklow to Prometheus or Datadog.
2. A **query** selects a family of measurements from that source.
3. An action **policy** says which series from the query may describe that action.
4. Arklow evaluates each eligible **series** in the context of the work it may represent.

One metric name can contain many series. For example, one query may return:

```text
request_latency{customer_id=C1, model_id=M1}
request_latency{customer_id=C1, model_id=M2}
request_latency{customer_id=C2, model_id=M1}
```

## Queries

Create queries on the metric source's **Queries** tab. A query holds the expression to use against your metric source.

Identity-tag exclusions remove selected provider tags when Arklow identifies a series. Use them when an operational tag changes without changing what the measurement represents.

<Note>
If you're using `Discover`, as detailed below - excluding tags that have high cardinality or aren't useful is recommended using the available dropdown on this screen.
</Note>

## Action policies

Open an action definition's **Metrics** tab and add a policy for a source query.

Arklow offers two unique modes for identifying relationships with your metrics. 

- `Manual` - You know what metrics/tags matters, and want Arklow to know it can just use what you already know to be correct.
- `Discover` - You have a rough idea that this query relates to the work being done, but you're not sure tags or relationships matter.



<Tabs>
  <Tab title="Manual">
    You pin known series with a selector of exact tag values. A series is eligible when it carries every key in the selector and its value for each key is one of the values you list:

    ```json
    {
      "customer_id": ["C1"],
      "model_id": ["M1", "M2"]
    }
    ```

    When a selector matches more series than the policy's maximum-series value allows, or matches several series with no maximum set, Arklow blocks the whole match rather than track a set you did not bound.
  </Tab>
  <Tab title="Discover">
    Arklow considers the series returned by the query and looks for the ones that consistently describe the action's work.

    The tags on your work tell Arklow which dimensions matter. A series sharing `model_id=M1` with your work is evaluated against exactly that slice of the work; a series with no shared tags is evaluated against the action as a whole.

    Use tag bindings when the work and metric use different names for the same dimension. A binding from action tag `customer` to series tag `customer_id` lets their values be compared without renaming either system.
  </Tab>
</Tabs>

The policy's maximum-series value bounds how many series Arklow tracks for that action and query.
