## Endpoint and authentication

Set **Endpoint** to the HTTPS base URL of your scale API, such as `https://scale.example.com`. Arklow appends the status path and the selected write path to this URL.

The endpoint must resolve to a publicly reachable address. Local and private-network addresses are rejected.

Use an [HTTP Auth Headers credential](/resources/credentials/http/auth-headers) for bearer tokens, API keys, or other headers your API expects. The same headers accompany observations and writes.

## Status endpoint

Arklow observes both modes with:

```http
GET {endpoint}/scale/status
```

Return `200` with a JSON object:

```json
{
  "current_replicas": 3,
  "desired_replicas": 3,
  "min_replicas": 3,
  "max_replicas": 3,
  "settled": true,
  "state": "running"
}
```

| Field | Type | Meaning |
|---|---|---|
| `current_replicas` | integer | The live replica count. Arklow treats this as an exact observation. |
| `desired_replicas` | integer | The replica count the platform is converging toward. |
| `min_replicas` | integer | The minimum replica count configured on the platform. The value can be `0`. |
| `max_replicas` | integer | The maximum replica count configured on the platform. |
| `settled` | boolean | Whether the previous change has finished converging. Defaults to `true` when omitted. |
| `state` | string | The platform state to record with the observation. |

All fields are optional. Return the values your platform can observe consistently.

Arklow uses `current_replicas` first as an exact observation. If it is absent, Arklow uses `desired_replicas` as a bound. If both are absent, Arklow uses `min_replicas` as a lower bound. Arklow always marks a bound observation unsettled, regardless of the `settled` field. Report `current_replicas` when your platform can observe convergence. A response with only `max_replicas` does not provide a replica observation.

When no bound observation applies, `settled: false` defers another write while the previous change converges.

## Write responses

A `2xx` response accepts a write. If the response includes a string `state`, Arklow records it as the write outcome.

A `4xx` response records a refusal. You can include an `error` string in the JSON body to describe the reason. Server errors and network failures appear as target errors.

Your endpoints should handle repeated writes of the same value safely. Retries and provider-side drift can cause Arklow to apply an accepted setting again.
